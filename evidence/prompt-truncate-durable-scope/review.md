Independent critique of the post-merge B4 commit-window evidence

The new probe substantiates the B4 read/write-window defect on main `b30f95ac4a80d2f6dbe3aa01001b0524314f6d74`, containing merge `0faf0938ebdc4420e11070822cf4f9db09eb4260`. I found no substantive fixture problem that invalidates the result. It is evidence of an incomplete **enforcing-mode depth backstop**, not a newly discovered issue, a physical-delete claim, or a contradiction of the current release's documented warn-only policy. No production correction was made or tested.

I independently inspected the final test and both final run logs, the registered submit path, the memory depth predicate, the actual SQLite writer and its transaction/lease guards, existing rollout and carrier tests, out-of-band adoption, and the cleanup fixtures. This critique evaluates the parent's executed receipts; it does not claim a separate test execution by the critic.

The final diagnostic file is [test_prompt_truncate_durable_scope.py](probe.py), SHA-256 `e92109f213737970c82f29d9aaecf8fe7b04f1c2a679e27502240890e64068ca`. [b4-final.log](probe.log) records Python 3.14.7 / pytest 9.1.1 under the sanctioned clean-environment runner: **one shallow control passed; one commit-window case failed** at its expected-4033 assertion, in 1.6 seconds. [b4-adjacent.log](adjacent.log) records 34 passes across the existing deep-truncation and two composite-carrier test files in 11.6 seconds. Those are selected checks, not a whole-suite result.

The ordering is convincing. Both real `SessionDB` handles initially see only `u0,a0,u1,a1`. Warm history carries the genuine durable row IDs, so row-ID resolution follows the ordinary stamped path. The request uses the real registered `handle_request` route, a valid ID for `u1`, `confirm_truncate=true`, and no deep confirmation. The wrapper on this particular database handle's `replace_messages` is entered after the production depth gate permits the cut. It asserts that warm history and version are still unchanged, then commits `u2,a2` through the second handle, verifies that the first handle sees the same committed physical snapshot, and calls the original writer. Thus the additional turn was absent at RPC entry and arrived between the safety decision and the real transaction. This is a deterministic legal interleaving across independent connections; it does not claim a probabilistic threaded stress test or an append after the writer acquired its SQLite write lock.

The same wrapper and public route run in the passing no-append control. That control archives only `u1,a1`, preserves the original prefix rows, writes the replacement user row, advances history version once, and records one worker dispatch. It helps rule out an invalid anchor, admission failure, blanket refusal, or a broken compute recorder as the reason for the negative result.

The execution boundary is appropriately bounded. `_run_after_agent_ready` is replaced with a recorder, the real worker thread is joined, and the fixture's already-present minimal agent has no deferred-build event, so `_start_agent_build` returns without constructing an agent. `socket.socket.connect` is forbidden. Target resolution, admission, depth calculation, persistence routing and the original database transaction remain real. This establishes worker dispatch, not model acceptance or live tool execution. The socket patch is a guard for this selected path, not a universal sandbox for every possible subprocess or networking API.

| Case | Writer-boundary durable state | Observed result | Interpretation |
| --- | --- | --- | --- |
| Shallow control | Four active rows; two user turns | Streaming, one dispatch, final active count 3 | Legitimate last-turn edit remains possible. |
| Commit window | Six active rows; three user turns | Streaming with new user row 7, one dispatch, final active count 3 | The writer archives both `u1` and independently committed `u2` without deep confirmation. |

The race receipt shows rows 3–6 changing from `active=1` to `active=0`, all with `compacted=0`. Rows 1–2 survive unchanged and row 7 is the replacement. Warm history becomes the two-row prefix, its version changes from 0 to 1, and the compute recorder is called once. These are direct effects captured before assertions and cleanup. The 4033 assertion fails first, so the subsequent no-dispatch/no-mutation assertions were **not executed** on the failing run. They specify the desired contract; the receipt independently demonstrates that the observed state violates each of them. Avoid describing those negative assertions as passing checks.

The source explains the effect without relying on mocks. `_archived_user_turns` in [methods_prompt.py](../../tui_gateway/methods_prompt.py:445) counts ordinary non-carrier turns from warm history; here it sees only `u1`. The durable loader is used for absorbed-carrier classification, not for an authoritative ordinary-tail depth check. Later, [replace_messages](../../hermes_state_messages.py:816) reads the actual live prefix inside `BEGIN IMMEDIATE`, then archives every active row at or beyond the divergent boundary. The mutation therefore covers the newly committed tail. `reject_active_turn_lease=True` remains enabled, but its in-transaction checks fence an active lease or compressor, not a changed durable drop set. The fixture does not disable those guards; it tests a completed independently committed append with no active turn/compression lease. Production [out-of-band adoption](../../tui_gateway/prompt_turn.py:507) explicitly supports other surfaces' appended turns, but that adoption runs in worker preparation after the destructive submit stage and cannot rescue rows already archived.

The requirement needs careful wording. [Programmatic integration](../../website/docs/developer-guide/programmatic-integration.md:76) explicitly says this release permits and logs unconfirmed deep cuts and a later release will refuse them with 4033 and write nothing. Main sets `DEEP_TRUNCATE_ENFORCED=False`; commit `10cf19374542c7a9bf0a8b5b144c9105adf09162` records the compatibility decision. The fixture scopes `True` to exercise that promised refusal branch, consistent with existing upstream tests. Consequently, this evidence supports “the hard gate still fails when enabled,” and does not justify “default main unexpectedly violates its present refusal contract.” The new test also does not establish that default mode logs this race as deep: the same stale predicate would classify it as shallow.

The expected unchanged database is the **post-append** witness: the independently committed `u2,a2` must remain present and active after rejection. `_snapshot` compares all message columns and the selected session counters (`message_count`, `tool_call_count`, `rewind_count`), together with warm history and version. That is strong evidence for the requested transcript-preservation contract; it is not proof that no unrelated table, active-slot registry, log, or session metadata can change during admission. Physical rows remain recoverable in the archive. This probe proves neither SQLite corruption nor provider/tool side effects, rollback correctness, or a recovery procedure.

The earlier cleanup warning is understood and resolved. The first fixture left its runtime registered while closing the database. The autouse `_reset_tui_gateway_server_state` later calls production session teardown before monkeypatch undo, and that teardown can read the still-referenced closed handle, triggering the reopen warning. The final fixture joins the recorder thread, releases the slot, removes its own runtime, restores the old global database, then closes both owned handles. The final log has no such warning. This cleanup occurred after the recorded scenario and did not explain the original streaming/archive result.

Two nonblocking improvements would make the probe easier to retain with a future fix. First, the hook asserts exact keyword-dictionary equality. A correct future implementation may add an expected-scope/CAS argument, and that assertion would reject it before exercising the writer; assert the required archival/lease flags while forwarding additional arguments. Second, the negative case checks code 4033 but not its documented `error.data`; in this simple physical transcript the prospective drop set is four messages / two user turns. These are test-maintenance and contract-coverage suggestions, not reasons to discard today's evidence. Any correction must bind validation of the actual durable effect set to the mutation transaction or an equivalent atomic guard; an earlier reload alone remains vulnerable to this demonstrated interleaving.
