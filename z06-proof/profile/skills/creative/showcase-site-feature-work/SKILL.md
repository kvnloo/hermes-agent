# Feature work on premium showcase sites

For sites whose value is high-fidelity pre-rendered imagery (Blender plates, gigapixel deep zoom), e.g. a robot showroom with theme/colour switching. Covers editors, customizers, generators and integrations added to such a site.

## Procedure

1. **Decide where it lives before building.** Default: a MODE of the existing page (toggle in the existing chrome), not a new route. Restate in one line ("edit mode on the home page: select a part -> existing camera zooms to it -> slim side panel") and confirm if the request is ambiguous. A separate page with its own UI was rejected as a toy and had to be torn down.
2. **Keep the fidelity source.** Never replace pre-rendered plates with a live WebGL/GLB approximation; browser PBR cannot match Cycles and the owner sees the downgrade instantly. Edits operate on the plates: selection from real per-object masks rendered from the locked Blender scenes (object-index/cryptomatte pass at plate resolution, one indexed PNG + parts.json per theme); colour/tone changes client-side on the masked region; generative changes through an image model on the masked crop, composited back inside the mask with a feathered edge at plate resolution.
3. **Match the existing design system.** Study the site's chrome components and global CSS first; reuse its type scale, spacing, colour tokens and motion. New controls stay minimal (hairline outlines, a status dot, a slim panel). Use `redesign-existing-projects` for polish checks.
   - Long-form/editorial pages follow the Hermes Agent site structure (hermes-agent.nousresearch.com): a darker brand-blue outer frame, a bright-blue hero panel framed by thin rules, then a large off-white paper pane (#f2f2f2) carrying blue ink (#0000f2): condensed display headings, tiny uppercase mono kickers, 1px blue rules, FAQ-style accordion rows (rule + plus icon) for collapsible deep dives, a faint ghost wordmark in the footer. A full-bleed brand-blue canvas for a whole reading page reads as "too blue". Keep product renders in full colour; don't copy Hermes' licensed fonts.
4. **Bring-your-own-subscription = local harness connector.** The page detects locally running tools and talks to them over HTTP: ComfyUI first (its ChatGPT-subscription node, then local models), any OpenAI-compatible URL, Ollama for prompt help. ComfyUI must run with `--enable-cors-header`; Chrome shows a Local Network Access prompt for https -> localhost. Hosted-provider OAuth sign-in is a later adapter: check the provider's token endpoint for CORS and its scopes before promising browser-only sign-in.
5. **Proof.** Unit tests on the pure parts (point -> part lookup, zoom-target math, mask composite with feather, theme save/load round trip); the repo's test/typecheck/lint/build; the existing page's contracts still green; a pixel-compare showing the normal page unchanged; headless screenshots labelled EMULATION; one real generation through the local harness with a receipt (prompt, output path, sha256, seconds). Cap real subscription generations per worker.
6. Local feature branch only; no push/PR without the owner.

## Deep-zoom infinite-canvas pages

For a zoomable portfolio/résumé world over a gigapixel plate (semantic zoom, tour, minimap, deep links), follow [infinite-canvas](references/infinite-canvas.md): overview shows only images and names, LOD keyed to absolute scale, lazy pointer capture, CSP style-src-attr, vendored coarse tiles plus streamed level 0.

## Refreshing site imagery from renders

When asked to check a project site and pull in the latest renders (often with "don't change yet, find the north star"), follow [render-refresh-audit](references/render-refresh-audit.md). Clone the site fresh (local checkouts go stale), read the owner's open issues and design doc first, inventory the newest renders by mtime across worktrees and artifact stores, triage them on a contact sheet, and publish only owner-approved stills with status and provenance labels.

## Turning a pretotype into the real company site

When a vision/landing site must become the owner's honest company site, follow [company-site-rebuild](references/company-site-rebuild.md). Run a security sweep first, build from a typed project manifest checked with `gh`/curl, and link every number to its source. OSS work names the upstream first. Use hash routes for Pages, add one focused e2e spec with axe, and compare legacy test failures against the base commit before treating them as regressions.

## Site-wide programs (performance, content pages, agent/GEO, GitOps)

- **One concern per branch.** Each feature gets its own branch and worktree so it can be tuned in isolation. A performance change goes on the branch that already owns that concern (tile decode, settle, touch, wheel). If that branch is stale, forward-port it as `perf/<concern>`, leave the original untouched and record the lineage. New concerns get new `perf/*` branches. Every change carries before and after numbers from the same harness.
- **Integration channel.** Feature and perf branches merge into a dated local `integ/site-<date>`, one branch at a time, re-running tests, typecheck, static build, the page contracts and the perf harness after each merge. On failure, stop that branch and record the block with its lane. dev and main move only through PRs the owner merges.
- **Plan for parallel lanes.** For a multi-lane program, write one PROGRAM.md (shared rules, lanes, branch names, output dirs). Give each lane a READY file listing branches, heads and evidence. Run the integration lane last: it polls for the READY files. When a running lane already owns a branch or surface, hand new work on it to that lane (steer it) instead of dispatching a second agent: two agents on one branch collide on leases and files.
- **Native-feel performance on 120 Hz phones.** The frame budget is 8.3 ms. Measure frame time p50/p95/max, input-to-next-frame, INP, LCP, CLS, deep-zoom HQ tile latency and route JS/CSS/image weight. Script real gestures (pinch, pan, wheel zoom, theme switch, long scroll) with Chromium touch emulation. Label numbers EMULATION unless they came from a real device, and give the owner a short phone test script. Long-form pages need responsive, fixed-dimension images: oversized images were the cause of a 7 s mobile LCP.
- **Validate a perf gate before it can block a merge.** rAF frame-interval cadence from headless, software-rastered Chromium on this shared, Blender-loaded host measures machine contention: identical code swung 2x between runs while page JS was ~1 ms/frame. Gate instead on per-frame main-thread work from the Chrome trace (callbacks + style + layout + paint + commit + main-thread decode) with >=10 interleaved A/B repeats, median + IQR and /proc/loadavg recorded; prove the gate by making a deliberately bad variant fail. Keep cadence as information; real 120 Hz is proven only on a phone. Validate visual-coverage sensors the same way before fixing what they flag: compare the sensor against what is actually painted on the same scripted journey (copied-pixel readbacks of every layer, plus a missing-layer control that must fail); a detail-only sensor can report hundreds of gaps where the floor and underlay layers cover every pixel, and a renderer change made against it is wasted. Fix an invalid method on the owning branch rather than lowering the threshold, and merge branches that do not depend on the blocked surface meanwhile. If the same gate is still red after two repair passes, stop dispatching passes: serve the candidate branch's static build on its own loopback port, open it for the owner to try, report per-metric pass counts (median p95 versus worst-frame tails), and ask how strict admission should be, with the phone test as the final check.
- **Many animated items (timelines, galleries of hundreds of thumbnails).** Per-item DOM animation misses the 120 Hz budget even with zero forced layouts, because layerization and paint dominate. Draw them on one WebGL2/Canvas2D surface from a thumbnail atlas with time as a shader uniform, one rAF loop, preallocated typed arrays and only a few DOM elements (accessible slider, caption, a handful of medium images). Ship the atlas lossy (WebP/AVIF at device-pixel size), load it after first paint starting with the visible range, decode in a worker and upload in slices: a large lossless atlas plus eager glyph preparation turns cold start into seconds of blocking time.
- **Locked design, perf rework.** When the owner locks a design, perf work changes only internals; prove it with same-state screenshot diffs on desktop and mobile before merging.
- **Test-browser routing.** The owner wants minimal-overhead browsers for agent testing: follow `light-browser-routing` (Lightpanda for DOM/functional checks, chrome-headless-shell for rendering, traces and Lighthouse).
- **Parallel lanes touching one page.** Several lanes adding imports or callouts to the same route file (e.g. the process page) conflict at integration. Keep shared-file edits minimal (wrapper classes, one import) and put the bulk in lane-owned CSS/content files.
- **Content for humans and agents.** Human pages are story-first (hook, tension, turning points, what we know now), in the site's poster style. Agent artifacts follow the owner's own `boplog` repo: llms.txt and llms-full.txt, agents.md, a data manifest with partitioned JSON, topic hubs, sitemap, feed, robots, OpenAPI and JSON-LD, plus its GEO benchmark. Locate repos the owner names in the local workspace first (`/mnt/zer0models/workspace/zer0/oss/<name>`); a similarly named public repo on GitHub is usually wrong.
- **Data pages.** Build them from a real pipeline: ingest, then normalise into SQLite with keys, indexes and integrity checks (dedupe, orphans), then export small content-hashed JSON aggregates. Scrub absolute paths, secrets and emails before publishing prompts or transcripts, and list any owner quotes for approval.
- **Internal HITL tools are content.** When a local review tool (for example a version-lineage viewer) proves useful, publish a path-scrubbed, virtualised web edition and link it from the process page as the tool used during creation.
- **Saving private tools to a public repo.** Check repo visibility first (`gh repo view --json visibility`). For a public repo, commit a dev tool's code with synthetic test fixtures, a README and a launch script only; its data (owner quotes, ratings, chat-derived labels, private renders, absolute paths) stays in the external artifact store, passed by CLI/env. Keep it out of the static export, and name the source of truth when the same code is mirrored in another repo.
- **Publishing code developed on a private branch.** Corrective commits do not remove private paths, quotes or IDs from earlier commits, so never push the development branch. Move project specifics (adapters, element maps, report globs, live-data verification tools) into a private adapter dir outside the repo and prove the live setup still produces identical outputs through it; build a fresh publication branch from the public base as one clean commit of the generic tree; audit every outgoing object (`git rev-list --objects origin/<base>..<branch>`) with a private-path/identifier scan, an owner-quote scan and gitleaks, zero findings required; then push and open the PR as a draft with `gh pr create --repo <owner>/<repo>` (on a fork, `gh` otherwise targets the upstream parent).

## Pitfalls

- Scoping the feature as a standalone tool page because it is easier to build: the owner thinks of features as states of the product they already have.
- A browser 3D export of the scene is fine as an internal artifact, never as the customer-facing view.
- Render large faint decorative text (ghost wordmarks) as an aria-hidden SVG: as live text it fails Lighthouse colour contrast.
- Render part masks from the SAME scene version that produced the shipped plates. Masks from a newer set (moved blocks, new step) share the camera but misalign wherever geometry changed; when plates and scenes are out of sync, say which parts are affected and re-render masks when new plates ship.
