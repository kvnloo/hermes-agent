# Switch Dash's phone services to a new integration worktree

The owner's phone loads Dash from user services on groot. Read the live layout before acting (`systemctl --user list-units | grep -i dash`, `systemctl --user cat <unit>`): currently persistent units `dash-bridge` (`:4747`, release checkout under `~/.local/lib/dash/bridge-current`), `dash-metro` (`--dev-client --localhost --port 18212`) behind `dash-metro-relay` on tailnet `:8212`, plus `z0bridge-identity`. Older setups used transient `systemd-run --user` units (bridge `:4747`, Metro `:8097`); the rules below about snapshotting transient units still apply when you find those.

## Rolling finished drafts onto the phone

The owner only sees what the served integration branch contains. Features left in unmerged draft PRs look to him like "you never built what I asked". So whenever a Dash worker finishes, roll it out promptly, and keep the feature ledger `/mnt/zer0models/workspace/zer0/data/operations/dash-feature-ledger.md` current (feature, live / in draft / never built, PR).

1. Merge the drafts into the integration branch in a SEPARATE worktree, never in the worktree Metro serves. Metro serves the working tree live, so a phone reload in the middle of a merge, or during a worker's follow-up fix edits, gets HTTP 500 "Unable to resolve <new module>". Every worker brief must say this: never edit, check out or stash in the served worktree; the only command allowed there is `git merge --ff-only origin/<integration>`, immediately before an idle-checked restart.
2. Qualify the exact merged revision through `fleet-build --node mbp`: app typecheck, the owning app/bridge/shared suite, export and mutation gates. Check `git merge-base --is-ancestor <peer-commit> <candidate>` before combining a peer's work; an already-included contribution needs no duplicate rebase or second rollout. Keep tested, staged and actually running SHAs distinct. Push accepted integration source and update any associated PRs.
3. Promote only after the exact composition qualifies, and restart only affected units after a fresh idle check. Inspect every unit's actual WorkingDirectory and the worktree's rollout-guard descriptor first. One checkout can serve both stable Metro and the bridge while its guard names only Metro. For a bridge-only release, do not overwrite that frontend lease or move the shared checkout to an app-changing union. With explicit operator approval, retarget only the bridge unit to a clean, qualified bridge-only worktree, preserving its private environment and credential paths; leave Metro and its checkout untouched. Keep rollback ready and read back the running PID's cwd, Git revision, health and authenticated APIs. Register the new runtime worktree with the existing served-record mechanism and read back its unit, port and hook coverage; freeze it in subsequent briefs. Validate that the rollout check understands the service's actual health contract: an auth-gated root returning401 is not a200 health check or proof that authenticated APIs work. Do not repurpose a frontend descriptor or disable owner-call checks to make a backend promotion pass.
4. Bind the runtime to the qualified source: read the unit's actual WorkingDirectory, its Git SHA, `/status` and the platform manifest. Check feature markers in the offloaded export rather than requesting an extra groot qualification bundle; the real client's bundle request is live-service work, not permission to run local build gates.
5. Launch-check the actual installed client within the owner's cleared UI window. Installed Dash uses its verified native development-client scheme and package; use the Expo Go package and `exp://` route only when Expo Go is actually the target. Follow `dash-native-dev-build` for the native launch procedure. Wait for expected application content and bundle/runtime evidence, not merely MainActivity or a fixed sleep. Reconfirm the foreground package before capturing and inspect the resulting image. Do not announce usability from a200 bundle, an early blank frame or green web fixtures.

## Fast path: JS-only update to the phone (`dash-channel`)

When the owner says "push the update to my phone", check first whether it needs an APK at all. The installed dev client on the S25 loads JS from the channel Metro (`dash-channel-metro`, tailnet `:8214`), which is separate from `dash-metro` `:8212` (`app-current`) and turbo `:8213`. Compare the candidate release's native fingerprint (the `native_fp` in `~/.local/lib/dash/channels/bin/dash-channel`: app deps, plugins, android package/permissions, newArch) with `channels/native-baseline`. Also explicitly diff local native modules under `app/modules/` and the native build inputs against the installed APK's qualified source; a fingerprint that omits local modules cannot establish APK compatibility. Only when both checks match, run `dash-channel add <name> <branch>`, then `build <name>`, `switch <name>` (health-gated), warm `curl -m 240 '<8214>/index.bundle?platform=android&dev=true&minify=false'` (about 60 s cold), then `dash-channel open <adb-serial>`. Verify with `dumpsys activity activities`: the intent must read `dash://expo-development-client/?url=…8214`. Then screencap. Rollback is `dash-channel rollback`. Before switching, run `git --git-dir=channels/repo.git rev-list --count <new>..<old>` and `<old>..<new>`. Then tell the owner what UI arrives or disappears relative to the channel he's on now. A branch hundreds of commits apart brings that branch's UI regressions with it, and he'll read them as "you broke it". Offer `dash-channel rollback` as the instant escape. After a switch, rebuild by hand when the worker pushes: the channel tracks the branch, but nothing re-serves it until `build`+`switch` (or nightly) runs. `build` dies with "exists but is incomplete" when the bridge release tooling has already made a bridge-only `releases/dash/<sha>` with no `app/node_modules`. Check that no process cwd or symlink uses it, then move it aside (don't delete it) and rebuild. `bridge-current` follows a separate path.

## Native APK delivery and live-preview continuity

- Preserve Turbo/live preview and QA mode when moving from Expo Go to an installed Dash app. Treat them as acceptance criteria in the initial build brief: use a development-capable build, retain the existing QA controls, and prove Metro/Fast Refresh over Tailscale on the installed package. JavaScript/UI changes should not need reinstallation; explain that native code, permissions and module changes do. Do not assume an Expo Go `exp://` launch URL also opens a native development client; verify the native client's actual launch link.
- Confirm approval before overriding an explicit Expo-Go-only project constraint for native capabilities. After approval, deliver the APK through ADB rather than handing the owner a manual download. Reconnect rotated wireless-debugging ports using the recovery procedure below, install with `adb -s <connected-address> install -r <verified-apk>`, and read back the installed package/version before claiming installation. Never equate a connected phone with an installed app.
- Report build, installation and device verification as separate milestones. If the owner asks where the app is, inspect the latest actual build result and whether an APK exists, then give the exact blocker promptly. A live worker, passing TypeScript checks or queued build is not an installable app. After a build fails, diagnose the failed stage before repeating it; do not leave the owner waiting behind generic progress promises.
- Verify native receiving and notifications on the device before calling them ready: share a real file through Android's chooser, confirm it reaches the intended draft without auto-sending, tap a real notification and confirm its chat destination. State separately which notification paths were tested; local notifications do not prove delivery while the app is killed.

## Review gate for design-bearing work

Workers that change what the owner sees (new views, legends, gestures, motion) stop at a pushed branch plus draft PR, and their REPORT lists screenshots made from REAL host data. The orchestrator writes the product spec (what each view answers, what each legend glyph maps to) and reviews those screenshots before merging. Sol-built UI shipped straight from its own fixture screenshots produced views that were "just words" and legend items the data could never produce. Visual and UX design goes to Opus (Nous reserve when Claude is throttled); Sol implements a decided spec. Every design brief must point at the owner's taste evidence: the `company-os-visual-language` skill and the cited profile `/mnt/zer0models/workspace/zer0/products/gev-showcase/taste/TASTE.md`. The fuller taxonomy lab, `/mnt/zer0models/workspace/zer0/products/taste`, is unfinished. Without that evidence, workers default to generic styling. When the owner asks for parity with omp's UI ("like omp x tern"), take the exact design from omp's source in `~/zer0/oss/oh-my-pi/packages/tui/src` (for example `status-line/context-usage.ts` `planCells`: a 20×10 grid with category cells, then free cells, then the autocompact buffer). Put the relevant excerpt in the worker brief. The source alone is not a picture. When the owner offers or asks for a look at the real omp UI ("go to a pane where omp is open and open the context menu"), render it in an idle omp pane: check that its composer is empty and its JSONL shows no recent owner turns; `/context` is a local built-in, so it runs no model turn. Screenshot it, look at it yourself, send the PNG to him, and attach it to the brief. Never word a status as if an image was captured or sent when it was only read from source. Motion stays fast-first: no visible overshoot on layout or graph moves, transitions ≤200 ms, and press feedback ≤80 ms. Use the shared tokens in `app/src/motion.ts`, not per-component springs, because the owner rejects bouncy motion that slows the app.

## Rules

1. **Snapshot the env and unit definition before stopping anything.** A transient unit created with --collect disappears on an explicit stop, so `systemctl start` cannot restore it. Capture its full service definition and prepare the exact recreation command (or an explicitly owned persistent service file) before a required offline switch; do not discover this after taking the preview down. Prefer an in-place idle-checked restart when no offline source transaction is needed. The transient units' `EnvironmentFile=`
   often points into a pruned scratch dir, so `systemctl restart` would fail.
   Read `/proc/<pid>/environ` into `~/.config/dash-services/env-*-owner-snapshot.systemd`
   (mode 600; it holds tokens). Never print it unredacted.
2. **Rewrite only obsolete worktree-local paths in the private snapshot**, such as Metro's `.worktrees/<old>/app/node_modules/.bin` PATH entries. Preserve credential/identity paths and unrelated settings; serialize values correctly for EnvironmentFile syntax and keep the result mode0600 without printing secret values.
3. **Prove the candidate first on a QA pair** (bridge `:4748`, Metro `:8098`, same env with
   the port changed) on the shared S22+. Wrap every S22 UI burst in
   `flock ~/.hermes/profiles/clean/cache/scratch/s22-ui.lock`. Other workers drive the
   same phone, so re-open `exp://100.113.138.100:<port>` and check `topResumedActivity`
   before you type.
4. **Stop the old units before you start the new ones** (never two Metros on 8097). Write
   the before, after and rollback commands to `~/.config/dash-services/switch-<date>.md`.
5. **Check logical work and owner activity before the switch.** Empty TCP queues or a disconnected phone do not prove an admitted model turn finished. Account for active turns, child/model transports, broker calls and pre-start voice buffers. Check journal coverage before counting starts/ends; rotated startup logs cannot establish full-lifetime coverage. Where using idle-by-exclusion, record the exact evidence and unmeasured buffer limitation, and hold if active work cannot be excluded. Check the phone foreground separately: watching video or reading another app is active use even with an old touch timestamp. An unanswered request to interrupt it gives no new permission; do background work and post a notification instead.
6. After the switch, read back the actual serving unit/PID/cwd/SHA, Metro's `/status` and native manifest, and the required authenticated backend responses. Use a history WebSocket probe when qualifying chat transport. Observe the real phone's bundle request and loaded UI rather than generating a separate groot validation bundle. Record installation, JS rendering, authenticated connection and physical input/media acceptance as different milestones.

## Pitfalls

- **Recovering from a500 caused by edits in the served tree:** identify the writer and coordinate stopping only the owned editing worker. Preserve tracked, staged and untracked evidence with `git-evidence-preservation`; do not automatically stash, reset or check out another owner's served tree. Recover and qualify a replacement in an isolated worktree, then use the approved idle-checked promotion or rollback path. Restart only the affected service, verify the actual client's loaded UI and runtime logs, and resume implementation in an unserved checkout.

- **Metro on this host misses newly created files** (inotify is exhausted). It hot-reloads
  edits but returns `UnableToResolveError` for a new module. Restart that Metro after you
  add files, then grep the bundle.
- **"[Reanimated] The easing function is not a worklet" at launch:** an inline arrow passed as `easing:` inside a function that also runs on the JS thread (initial `setPage`, mount effects) is not workletized. Give every easing closure its own `"worklet";` directive, or return it from a worklet factory in `src/motion.ts`. Then rebuild and launch-check on the phone.
- **S25 adb `device not found` / `Connection refused`:** wireless-debugging ports rotate. Scan with `nmap -Pn -p 30000-49999 --min-rate 3000 <tailnet-ip>` and use timeout-wrapped `adb connect` calls for discovered ports. Require `adb -s <address> get-state` to return `device` and verify `ro.product.model` plus `ro.serialno` before installing or updating `~/.local/state/z0live/phone-adb.json`. An open TCP port, successful Tailscale ping or an `offline` transport does not establish an authorized ADB connection. If one bounded recovery pass leaves every candidate offline, report that exact boundary rather than repeating the scan indefinitely or claiming a diagnosis of pairing failure. Continue independent server-side work; request only the missing phone-side action, without presenting an unverified toggle/re-pair suggestion as a proven fix.
- **"Dash not connecting" triage, in order** (screencap the phone after each fix and read the error text — each layer has its own toast):
  1. Stuck on "Reloading…": Metro serves fine but the cold bundle build takes ~1 min; warm it with `curl -m 90 '<metro>/index.bundle?platform=android&dev=true&...'` (second fetch <1 s), then relaunch with `am force-stop app.dash.mobile` + the `exp+dash://expo-development-client/?url=<encoded metro>` intent.
  2. "z0bridge request failed at /.well-known/jwks.json": the identity-only z0bridge (loopback 4789, tailnet 4788) is down. It must be a persistent enabled user unit (`z0bridge-identity.service`: `z0bridge serve --harnesses none --identity-host <tailnet-ip> --identity-port 4788 --port 4789 --issuer z0bridge:groot`, `Environment=DASH_HOST=<ip>` for the `dash-wait-tailnet` pre-start) — a transient process vanishes on host reboot. Check the served JWKS kid equals `~/.config/z0bridge/identity.json` kid so existing pairings stay valid; `z0bridge devices` shows the phone credential's last-used time.
  3. "Can't reach the bridge" while TCP to :4747 connects: the bridge lacks identity opt-in and rejects the phone's JWTs. Keep `DASH_IDENTITY=1`, `DASH_IDENTITY_URL/ISSUER/KID/CREDENTIAL_FILE` (verifier cred at `~/.config/dash-services/z0bridge-introspection.json`) in a drop-in `dash-bridge.service.d/50-z0bridge-identity.conf`, not in the release-owned `bridge.env` — rollouts replace that symlinked env file and silently drop the identity block.
- **"Voice doesn't work" triage, server first, then client:**
  1. `journalctl --user -u dash-bridge | rg '  voice '`. A startup line `voice unavailable — No speech model at …/tiny-models/…parakeet…` means the bridge's on-host STT model is absent. Copy that directory from a host that has it (`rsync -a mbp:.omp/agent/cache/tiny-models/csukuangfj/<model> ~/.omp/agent/cache/tiny-models/csukuangfj/`) or run `omp setup speech`. `speechAvailable()` re-checks on every request, so no bridge restart is needed. Prove it by importing `bridge/speech.ts` from the live release with `bun` and running `transcribe()` on a 16 kHz wav.
  2. Live voice (the (( • )) button) goes through `POST /voice/bootstrap`. It returns 503 unless the bridge env has `DASH_NATIVE_VOICE=1` (drop-in `60-native-voice.conf`; check `/proc/<pid>/environ` for that key only). After bootstrap it uses the z0live broker on `:8791` (`z0live.service`; an unauthenticated 401 there is normal).
  3. For the identity-backed native path, inspect the running broker PID's cwd/revision and only the relevant environment keys: `Z0LIVE_IDENTITY` and the presence of its introspection credential configuration. Reconcile these with the qualified attached-voice candidate, the exact phone credential's `z0live:voice` grant and the authenticated bootstrap response. `DASH_NATIVE_VOICE=1` on the bridge does not enable identity acceptance in an older broker; public JWKS success or an unauthenticated401 does not prove interoperability. Follow `z0live-voice-work-tools` for qualification and scoped deployment; do not widen grants merely to make a probe pass.
  4. If neither the bridge nor the z0live journal shows any voice/bootstrap request after the owner's tap, investigate client execution and phone-to-bridge connectivity before attributing the failure to one of them. The dev client's JS logs don't reach the channel Metro journal. Capture bounded app-PID logcat around one authorized tap (don't drive his daily phone while he's using it), and correlate the client error with both server journals.
  5. Decide refresh versus APK versus backend deployment from this complete path, not just the preview symlink. When asked why rollout is delayed, lead with the observed missing deployment stage and the next executable action. Distinguish code qualified, backend served, APK installed, JS loaded and real audio verified; a completed worker report or a running qualification job does not deliver the feature. Recover existing receipts before submitting another full run, and keep ADB recovery separate from server qualification so a disconnected phone does not stall all progress.
- Bridge code does not hot-reload. Restart the bridge unit after bridge commits.
- Do not run `git stash pop` or `git checkout <sha> -- .` in a shared worktree to compare
  revisions. Use a separate `git worktree add` instead.
- `bun test` with no arguments also runs `docs/**` tests that have known stale
  failures. The gate is `bun run test`, `bun run typecheck` and `bunx eslint . --max-warnings 0`.
