# Reference-driven UI styling

## Procedure

1. Inspect the actual reference images and current rendered UI before prescribing changes. Locate existing project inspiration assets and compare them with the running interface, not just source CSS. When the user asks for analysis before design or code, finish a source-backed breakdown of composition, observed interactions, asset requirements and verification criteria first; do not substitute a generic design direction for inspecting the supplied reference.
2. Establish the requested axis of change. For this user, matching design language or style means typography, geometry, surfaces, palette, iconography and interaction treatment. Preserve dynamic content and density unless the user asks to restructure information architecture. Do not answer a styling question primarily with a content-reorganization plan. If the user explicitly asks for a literal initial-frame replica, use the reference composition and fixture content instead of adapting dashboard density or merging another design. Follow [video-frame replication](references/video-frame-replication.md); keep fixture labeling and comparison controls outside the composition.
3. Extract the clean visual grammar. Separate intentional dots, hairlines, rings and halos from compression grain, ringing and pixel noise. Recreate intended graphics with crisp CSS/SVG; never add texture merely because a compressed reference looks noisy. Inspect the exact linked video frames before attributing any design decision to a clip; if the issue only describes a conversation upload and provides no locator, record the missing URL/upload as a blocker and use the established still/source fallback without inventing video findings.
   For motion-fidelity requests, contact sheets and functional UI tests are not extracted animation data. Track native-frame element geometry, fit timing/easing with residuals and uncertainty, and verify intermediate choreography against the source. For filmed displays, stabilize the monitor plane or static bezel/UI landmarks before attributing motion to the website; report normalized visible-viewport travel when CSS viewport size/DPR are unknown. If the owner points to their skill forks, inventory their live repositories and read the relevant skill sources and indexes before selecting an extractor. A linked extractor is not necessarily one of their forks. Distinguish discovery, a prepared run, an admitted run and measured output; never promote estimates when worker admission is blocked.
   Separate decode, tracking and fitting when a video pipeline is blocked. Verify FFmpeg CUDA/NVDEC with real decoder logs rather than assuming GPU use; a CPU-only tracker does not block GPU frame acquisition. With filmed displays, reject an ill-conditioned homography from collinear wall/bezel points; fit a constrained camera model and apply monitor-plane rectification separately. For color tracking, union relevant disconnected components inside a temporal ROI so a blue toe is not lost when it separates from a blue heel; for a partly phone-occluded bottle, track its unoccluded cap and keep rejected frames flagged. Validate first/intermediate/final annotated boxes before fitting. A persistent camera scene must freeze its grid tracks, gaps, card dimensions and product/shelf local rectangles while open; otherwise a viewport breakpoint can reflow the world underneath captured coordinates and hide the selection. Account for containing-block borders when converting DOM rectangles into absolute child positions. Test resizing an open scene both ways across the mobile breakpoint. After rapid sequential edits, verify the actual served transform includes the final prop update; run final acceptance on a fresh production bundle rather than trusting Vite HMR state. Treat fitted duration/Bezier parameters as an effective reconstruction, report native-frame resolution and active-window errors, and do not claim recovered source CSS or confidence from residuals alone.
   A cap-width easing fit alone does not validate bay choreography. Measure initial/final bay boundaries, selected-object centers and cap height, neighbor travel/fade and metadata reveal timing. Match the gallery's column count and starting spacing before retiming; a different starting grid changes the approach distance even with the same curve. Keep late-revealed controls inert until arrival, and exclude inert descendants from a modal's Tab trap. Freeze grid justification and item alignment as well as tracks: switching `justify-content:center` to `stretch` can shift a frozen world despite identical track widths. Check decoded bitmap dimensions and alpha footprint against transformed CSS size times DPR; gallery `sizes` and density-corrected `naturalWidth` can conceal a low-resolution hero. Decode the full hero before moving, remove the gallery srcset constraint for detail, and label learned restoration as inferred detail rather than native generation.
   For social-video references, resolve the share URL and inspect the actual media, not just the post thumbnail. Read the loaded video's `currentSrc` and duration, download it when accessible, then inspect a whole-clip contact sheet and native frames of each distinct gallery/detail state. Separate filming perspective, display glare and camera motion from website effects. Do not infer true 3D rotation, cross-device synchronization or working commerce from a filmed demonstration alone.
   For a live reference website, measure instead of eyeballing: fetch the HTML, download its CSS chunks (`grep -oE 'href="[^"]+\.css[^"]*"'`), then grep `:root` custom properties, `@font-face` families, hex-colour frequency and container `max-width`s. Report the real tokens and the structural surfaces (frame, hero, reading pane) to the implementer together with a before full-page screenshot. Do not copy licensed fonts; keep the project's own type when it reads similarly.
   When porting an existing app's look to another surface, matching tokens is not enough: blur, sheen gradients, rim highlights and pill shading live in the component source. Take the reference from the build the user actually runs (check the running dev server's cwd, not the newest branch). Sample pixels from the user's real screenshots, and copy the component recipes instead of re-deriving them from tokens.
   When the user says a page is "too <colour>" against a reference that uses the same colour, the fix is usually proportion and structure (which surfaces carry the brand colour vs a neutral reading pane), not a palette swap. Check whether the tokens already match before proposing new colours.
4. Inspect the existing framework and shared presentation boundary. Apply a coherent token/component system rather than migrating frameworks or creating a competing dashboard. Define light/dark surface, text, line, accent, typography and interaction tokens before changing individual panels. For a reference-led product showroom, create and inspect the requested original product assets before tuning the layout; keep product photography, shelves, reflections and light as separate layers so transitions remain continuous and responsive. Follow [generated product showrooms](references/generated-product-showrooms.md) for isolation, sizing and shared-image motion checks.
5. Apply the grammar across representative component densities: dense tables, expanded evidence details and sparse network views must remain recognizably the same interface. Reference composition and sample labels are not mandatory layouts or architecture.
6. Preserve semantic truth during styling. Keep unknown, stale, degraded and observed states distinct. Do not add fake progress, telemetry, voice waveforms or animated execution; decorative motion must not imply witnessed activity.
7. Verify existing interactions and inspect actual rendered screenshots in both themes, with dense/sparse and outage/unknown states. When this user rejects visual fidelity despite passing tests, reopen the visual acceptance criteria: add the missing source-observed dimensions before changing implementation, and keep regression counts separate from evidence of matching appearance. Compare opening, intermediate and settled states; do not present a small easing residual or a larger green test count as proof that the effect now feels right. Distinguish proposed design changes from implemented and exercised changes. When asked to show a visual artifact, open the canonical artifact in the requested application and verify the target changed, rather than supplying only a path.

## Native-feel app shells (editors, studios, creative tools)

This user wants web apps to feel like native desktop apps. Standing rules:

- **Fit the window.** On desktop (>= 1024 x 600) the shell is exactly `100dvh` with no document scroll; every panel scrolls internally. Primary work regions (canvas, timeline, inspector) are always fully visible; secondary panels (versions, assistant, provenance) live in tabs or collapsible docks, never below the fold. Short heights shrink the canvas first. A long scrolling page reads as a website, not an app.
- **Own the right-click.** Replace the browser context menu app-wide except inside inputs/textareas/contenteditable (keep native copy/paste/spellcheck); menus are keyboard navigable (Shift+F10, ContextMenu key), show the user's current keybindings in platform form (Ctrl+Shift+U / ⇧⌘U, never `Mod+...`), and run through the same undoable command path as buttons.
- **Follow the desktop theme without losing identity.** Map the system palette (Omarchy, Noctalia, pywal, GNOME/KDE, browser fallback) onto the product's own tokens so the system colours restyle the product's structure; never fall back to a generic skin when following the system. Contrast-correct automatically.
- **Verify at the user's real window size first**, then a viewport matrix. Get it from the compositor (Hyprland: `hyprctl -j clients` for the browser window size, minus browser chrome) and gate the matrix in the repo's verify harness. Recipe: [app-shell viewport matrix](references/app-shell-viewport-matrix.md).
- When the user reports seeing something different from your screenshot, check which project, state or stale tab they opened (e.g. a project without audio shows a one-row timeline) before assuming a regression, then still audit the layout.

## Static editorial shell checks

- Put hero and paper palettes on separate scoped ancestors; mutate root theme tokens in the browser test to prove home navigation cannot leak into the article. Keep the dark frame on the route root, not global body styles.
- Preserve native `details`/`summary` when applying FAQ styling. Draw plus/minus as CSS decoration, retain focus rings, and exercise Enter/Space with JavaScript disabled. CSS `text-transform` changes browser `innerText`, so preserve existing status-text contracts rather than weakening tests for a cosmetic change.
- After widening word spaces in a condensed heading, inspect every target viewport again: a small spacing improvement can wrap an explicitly two-line hero into three lines. Adjust the display size or measure rather than removing the improved separation.
- Compare exact before/after exports with identical Lighthouse settings and retain failed/incomplete trials. Zero layout shift in a final series does not erase an earlier nonzero result; a tiny positive median LCP delta is not proof of a strict no-regression budget. Distinguish a feature's older image pipeline from a newer integration baseline.

## Showcasing a material or visual library

These rules apply to docs or landing sites for an asset library (material packs, textures, imagery):

- **The product's own imagery is the design.** Lead with the best real assets: a full-bleed hero, a wall of real materials, and cards whose whole face is the image. Never use emoji feature grids, coloured placeholder boxes or a generic logo where real assets exist. Stock framework themes (VitePress default and similar) read as low quality to this user. Restyle from the library's own CSS tokens: palette, serif display type, radii and focus ring.
- **Glass over material, not panels over material.** UI floats on the material as frosted glass: `backdrop-filter: blur(~20px) saturate(170%)`, a bright top inner edge, a faint rim and a soft shadow. Do not use opaque grey slabs, which hide the material and make everything look grey. Put a smoky base tint (about `rgb(16 18 20 / .3)`) under the glass so white text stays legible on pale materials such as water, nacre and limestone. Make the nav and sidebar glass too, so content blurs behind them instead of showing through.
- **Preserve native masters and enough real pixels for the largest displayed detail.** Smaller responsive gallery derivatives are appropriate, but do not reuse them for a transformed hero or mistake transparent canvas padding for product detail. Regenerate poorly framed sources when needed; label restoration as inferred detail, not native generation. See the `chatgpt-image-generation` resolution reference and [generated product showrooms](references/generated-product-showrooms.md).
- In VitePress, bind attributes on custom elements with `:attr.attr=`. A plain `:attr` sets a DOM property, which a read-only getter silently drops. Restart `vitepress preview` after every rebuild: it keeps serving the old asset hashes, so pages render unstyled.

## Cockpit visual grammar

For restrained instrument-panel references, use narrow monospaced labels, tabular values, carefully tracked short labels, hairline connectors, small circular junctions, diamonds and open corner brackets. Preserve readable explanatory text instead of applying wide tracking everywhere. Prefer consistent thin-stroke vector icons over noisy raster extraction.

Use warm off-white and dark text for light surfaces, near-black and soft white for dark surfaces. Keep accent color restrained and meaningful; faint localized halos can provide depth without broad glows, glass cards or chunky shadows. Choose dot-matrix treatments only where intentional, not as a global texture. Density may change without changing this grammar.
