# Secure provider onboarding

Kevin's rule: agents never see or touch anything secure (bank, cards, personal mail contents beyond the verification message, his main password vault). Agents may create *developer-service* accounts and API keys, but every secret value stays out of tool output, screenshots and chat.

## Standing rules
- **Do the whole flow yourself.** Kevin expects signups, logins, alias creation and key capture to be done by the agent with the built-in tools (Hermes vault, Bot Screen, password-manager autofill, cua-driver). Do not hand back links or "please log in" steps when a tool can complete them; hand off only a step that genuinely needs a human (CAPTCHA, phone/SMS, ID check, payment) and use Bot Screen takeover for it.
- **Read the docs of the installed version before improvising.** Read `website/docs/user-guide/features/{bot-screen,credential-vault,browser,computer-use}.md` in `/workspace/hermes-home/hermes-agent` (the checkout Hermes runs from) and the catalog (`plugin-catalog/*.yaml`, e.g. `hermes-proton` for Proton Mail tools). Only build a custom helper for a gap those docs confirm.
- **Judge "is Hermes out of date" against its update channel, never against `main`.** `hermes --version` and `grep -n 'Update channel\|Release' ~/.hermes/logs/update.log | tail` show the channel; on `stable` a checkout is current when it sits on the latest stable tag (`git describe --tags`), and thousands of commits behind `main` is normal. Reporting the `main` gap as staleness alarms Kevin over a healthy install. `cua-driver check-update --json` is the driver's own comparison.
- Never type a password with cua `type`/`type_text` or `browser_exec`; passwords enter pages only through `browser_vault` or a password manager's own autofill.
- When local compute is short, Kevin authorizes signing up for free-tier or trial compute providers yourself (no CAPTCHA, phone or payment step). Probe each signup page for its auth methods and challenge scripts before starting; prefer email magic-link or email/password flows with the alias. Provider status, signup walls, the headless CLI device-login recipe and the GPU-offload decision table: `references/free-compute-providers.md`. A provider counts as working only after a real job of the needed kind ran there; billing walls show up at first use.
- Never solve CAPTCHAs, never add a payment method, never multi-account a free tier, never sign up to reverse-engineered proxies of other vendors' chatbots.
- $0 spend guard on every new signup (owner rule): keep the account on its free/trial tier (never upgrade to pay-as-you-go), set the provider's own hard cap or budget alert where one exists, and record it in the signup queue. Oracle tenancy: quota policy `always-free-only` (only A1 4 OCPU/24 GB, 200 GB block storage, zero DB) + budget `zero-spend` ($1, alerts at 1% actual and forecast to the account email).
- Harness-only providers: see the section below.

## Procedure
0. **"New subscriptions/keys exist" with no names given:** inventory before acting, in one batch. Sort bws keys by `revisionDate` (`bws secret list -o json | jq -r 'sort_by(.revisionDate)|.[-10:][]|"\(.revisionDate) \(.key)"'`, keys only), check `burn-pace --json` lanes, `browser_vault list`, the pool rows in `~/.hermes/auth.json`, and the signup queue's `account-only` rows. Then open each candidate console signed-in and read its plan banner. A console still showing "Upgrade"/Free plan is not the new subscription, so don't create keys there. If nothing identifies the new plans, ask which services in one line, listing what you checked.
   - **The new plan is a Claude subscription already in Hermes** (a row in `~/.hermes/auth.json` `credential_pool.anthropic`): don't start a new `hermes auth add` OAuth. Copy from Hermes instead; see "Share a Hermes-held Claude subscription" below.
1. **Preflight** (rules above): versions + docs; `hermes -p clean computer-use screen status`. Check `MemAvailable` first: the Bot Desktop refuses to start below `bot_desktop.min_free_memory_mb` (1536 MB), and on a starved host the memory guard kills the screen and its Chromium mid-flow. Wait for headroom with a bounded background script (notify on exit) rather than relaunching repeatedly; the browser profile keeps the session cookie across a relaunch. Bot Screen = a per-profile Xvnc/Xfce desktop with one persistent headed Chromium that `browser_exec`/`browser_vault` drive; Kevin takes over in Hermes Desktop for CAPTCHA/2FA and hands back with the session kept. Setup, the host-browser wiring and the phone takeover viewer: `references/bot-screen.md`.
2. **Identity:** prefer "Continue with Google" as **veeman961@gmail.com** through `kchrome google` (it picks only that account, and stops if another account is selected or veeman961 is missing). Kevin prefers it because it needs no password or verification mail. Where Google sign-in isn't offered, use the Proton alias `agents.purely464@passinbox.com` (Proton Pass `agents` vault, forwards to his Proton inbox). If a site rejects passinbox.com as "Email invalid" (Mistral does), use `kvnloo+<site>@proton.me`. If an account chooser offers an account these rules don't name, ask; never pick one by guessing, because redoing a signup on another identity makes duplicate accounts and can lose per-account free credits.
3. **Password:** `~/.hermes/profiles/clean/bin/vault-gen-login <origin> <email> [label]` - Proton's offline generator (`pass-cli password generate`) -> encrypted Hermes vault bound to that origin (copy to Proton `Agent Signups` if a scoped agent session exists). Prints only the handle. Then `browser_vault(action="fill", handle=...)`; result `{filled_fields: 1}`. Codes: `browser_vault(action="enter_code")`.
4. **Email verification:** `bin/proton-mail-code KEYWORD OUT [--link REGEX]` searches Kevin's Proton Mail in his Chrome on :20 and copies the message through the X clipboard. It writes the first 6-digit code (or the first matching link) to a 0600 file and prints only its length. Insert the code from that file inside browser_exec (`cdp('Input.insertText')`) and delete the file in the same call. `browser_vault enter_code` cannot ask Kevin from an ACP session. Older recipe for his Hyprland Chrome: `references/kevin-chrome-cua.md`. Never screenshot an open verification message.
5. **Key capture:** in Kevin's Chrome, `kchrome copy-to-bws ENV_NAME "<copy button label or sk- prefix>"`. It clicks with a real pointer, because some sites copy only on a trusted click. Check `kchrome ls` for `table cell 'sk-...'` when a site has no copy button. In the Bot Screen browser: `capture_key_to_bws(selector, ENV_NAME, note)` from the browser_exec workspace `agent_helpers.py` (reads in-process, stores to bws, verifies read-back, blanks the DOM; returns name/id/length). Validate the key against the provider API in the same browser_exec call before storing. Read key pages only with `safe_text()` (masks token-like strings).
6. **Wire it:** add the key to the `hermes-root` scope in the live bws-consumers config *and* the `.files` source (`config/bws-consumers.json`, PR), then `hermes gateway restart`. Built-in providers read the env var named in `hermes_cli/auth.py`; custom OpenAI-compatible ones go under `providers.<name>` (`base_url`, `key_env`, `api_mode: chat_completions`, `default_model`) plus a `model.aliases` entry via `hermes -p clean config set` (the patch tool refuses Hermes config). Smoke per the usage-file pitfall below. `hermes gateway restart` is refused from inside a gateway-run session, since the restart would kill the caller. The guard also catches detached wrappers (`systemd-run --on-active`), so don't try to route around it even when Kevin says "restart it yourself". Ask him to run it from his own terminal, and say in the report which new keys and providers wait on it.
   - A provider counts as done only after a real chat completion. Several signups now give an account with no free inference: DeepInfra and Together need a balance, Mistral's API keys need a paid plan, and SambaNova's free tier may answer "high demand". SiliconFlow's free models can 402 "insufficient balance" on one account while working on another, since free access is granted per account. Z.ai's `glm-4.7-flash` is free while `glm-5.*` needs a balance. Record the no-inference ones as `account-only` in the queue, not `done`, and probe each model you route to.
7. **Record** state in the resumable queue `/mnt/zer0models/workspace/zer0/data/operations/free-tier-research/20261102/signup-queue.json` (`state`, `vault_handle`, `bws_key`, `blocker`).

## Other auth flows
- **MCP OAuth** (e.g. AgentWeb Emma): run `SSH_CLIENT="127.0.0.1 1 1" DISPLAY= WAYLAND_DISPLAY= hermes -p clean mcp add <name> --url <url> --auth oauth --connect-timeout 1800` under `script -qfc` in the background, read the authorize URL from the log, then complete the consent in a signed-in browser (Bot Screen or Kevin's Chrome) yourself. The default 30 s connect timeout kills the flow before anyone can click.
- **Proton Pass CLI**: `pass-cli login` can end with "account not yet allowed to use our CLI" (Proton gates the CLI per account); then do vault/alias work in the Pass web app instead. `bin/proton-agent-setup` (scoped 1-vault agent token -> bws `PROTON_PASS_AGENT_TOKEN`) is written from `--help` only; verify its token regex with `pass-cli agent instructions` on first real use. Running `pass-cli` from a scratch dir: set `TMPDIR=/tmp`, or session persistence fails on the temp file.
- Fallback broker with its own Chrome profile: `bin/signup-broker` (`page ...`, `secret gen-fill|fill|capture`, deny list, audit log `~/.local/state/signup-broker/audit.jsonl`). Prefer the Hermes vault path above.

## Share a Hermes-held Claude subscription (bws + T3 Code)
Preferred when Kevin wants "long-standing keys": `claude-longkey <ultra|sub2|main>` (in `~/.local/bin`) runs `claude setup-token` (1-year token), stores bws `CLAUDE_<A>_LONG_TOKEN`, adds Hermes root pool row `claude-<A>-long` at priority 0, writes `~/.config/claude-long/<A>.token` (the `t3-claude-<A>` launchers prefer it) and smokes it. It needs Kevin's browser sign-in per account; from ACP, offer the authorize URL in a `request_secret` card (`delivery: file`, `timeoutMs` <= 280000, because the MCP call itself times out at 300 s).

Hermes PKCE pool rows hold an ~8 h access token plus a refresh token that rotates on use, not a long-lived token. Keep Hermes as the only refresher, because two programs refreshing their own copies log each other out.
1. **Vault:** store the row as JSON `{label, access_token, refresh_token, expires_at_ms, source}` in bws as `<LABEL>_HERMES_GRANT` (e.g. `CLAUDE_SUB2_HERMES_GRANT`), with a note saying it is a restore-only snapshot. Build it with `jq` inside one subshell, `create` or `edit` it, then read it back and compare in-shell (secrets-manager-bws procedure).
2. **T3 Code:** each `claudeAgent` provider instance in `~/.t3/userdata/settings.json` points at a wrapper `~/.local/bin/t3-claude-<label>` with its own `homePath`. The wrapper reads the live row from `~/.hermes/auth.json`, runs `hermes auth refresh anthropic <label>` (HERMES_HOME=~/.hermes) when the token expires within 2 min, clears `ANTHROPIC_*`/`CLAUDE_CODE_OAUTH_TOKEN`, and execs `claude` with `CLAUDE_CONFIG_DIR=~/.claude-<label>` and `CLAUDE_CODE_OAUTH_TOKEN=<access_token>`. Copy `t3-claude-ultra` and change the label and config dir. A plain `CLAUDE_CONFIG_DIR` wrapper breaks once that dir's `.credentials.json` has been moved into Hermes.
3. **Prove it:** `~/.local/bin/t3-claude-<label> -p "Reply with exactly: OK" --model haiku --output-format json | jq '{result,is_error,modelUsage}'` for each wrapper. Calls straight to `api.anthropic.com` (e.g. `/api/oauth/profile`) are refused by the O19 spend guard; compare tokens by sha256 fingerprint instead.

## Harness-only providers (owner rule)
Gemini is used only through agy; OpenCode Zen only through the opencode harness. Hermes may launch those CLIs as subprocesses (`agy -p "..." --model gemini-3.8-flash-low --print-timeout 120s`; `/usr/bin/opencode run -m opencode/<id>-free "..."`, ids from `opencode models | grep ^opencode/`). Never call their APIs as Hermes providers, MoA members, probes, scripts or vLLM-SR backends, not even a `/models` list. `GOOGLE_API_KEY`/`OPENCODE_ZEN_API_KEY` stay out of `hermes*` bws scopes; `.files` `tests/test_bws_scopes.py::HarnessOnlyProviders` enforces it. Keep chiefstaff MoA presets that used gemini/opencode-free disabled.

## Remote MCP OAuth from Kevin's phone (Tailscale)
- Hermes's OAuth listener binds only 127.0.0.1:<port>, so the phone's redirect fails. Default callback wait is 300s; set `mcp_servers.<name>.oauth.timeout: 3600` (connect_timeout alone does not extend it).
- Today's working path: run `hermes -p clean mcp login <name>` under `script` in the background, send Kevin the authorize URL, he pastes the `127.0.0.1:27890/callback?code=..&state=..` URL, replay it with `curl` on groot within the timeout. Emma (21 tools) was connected this way.
- Tailnet path (prepared, untested end-to-end): `tailscale serve --bg --https=27890 http://127.0.0.1:27890` is live (tailnet-only, 502 while no listener). For a new server set `oauth.redirect_port: 27890` and `oauth.redirect_uri: https://0.taila30dc.ts.net:27890/callback` before its first login, so the provider redirects straight to groot over the tailnet. Don't change redirect_uri on an already-registered client without re-registering.

## Pitfalls
- Run `bin/kchrome-up` before any kchrome work (restarts the Bot Screen, Kevin's Chrome and the cua socket if they died). `bin/kgs URL` = open + real-click the Google button + pick veeman961 + list the page.
- If the login keyring is locked (`busctl --user get-property org.freedesktop.secrets /org/freedesktop/secrets/collection/login org.freedesktop.Secret.Collection Locked` -> true), bws and Chrome's Google cookies both fail and secret-tool hangs. One request_secret (delivery file) -> `bin/keyring-unlock FILE`. A keyring dialog on :20 owned by a gnome-keyring on a /tmp/dbus-* bus is the Bot Screen's private keyring: cancel it, never type Kevin's password there.
- Keyless sweep done 2026-11-04 (`$TMPDIR/keyless_probe.py` over providers.json): only free.ai answered beyond OVH/Pollinations/Kilo/LLM7.
- Perplexity web sign-in is an email OTP (6 boxes) to the alias. `proton-mail-link` finds no link (the message body is not in the AX tree), and `browser_vault enter_code` reports "No page with a code field" for the 6-box widget. Hand the code step to Kevin through a Bot Screen takeover.
- Verify a provider/model smoke through `--usage-file`: run `hermes -p <profile> --provider X -m Y -t file --usage-file f.json -z "Reply with exactly: OK"`, then require `api_calls >= 1`, `failed false` and `model == Y`. Reply text alone does not prove which provider or model served the call; `--provider` overrides have silently fallen back to the default model. If the usage file is missing or shows another model, check `sessions.model` in `state.db` or probe over direct HTTP. A `model.aliases` entry (`-m <alias>`) routes reliably.
- A 200 is not an inference receipt: retired endpoints (GitHub Models) still return 200 with a plain-text body. Parse the JSON choice.
- NIM `/v1/models` lists models the account cannot invoke (404 "Function not found") or that time out; probe each model before routing to it.
- Kilo Gateway free models are all flagged `mayTrainOnYourPrompts`; LLM7/Kilo/free.ai are keyless public routes - public or scrubbed data only.
- `agent_helpers.py` helpers must `from browser_harness.helpers import js`; they are injected into browser_exec, so `import agent_helpers` inside a call fails.
- Local test servers: bind port 0 in-process; fixed ports (8765, 18765) are taken by Kevin's services and serve a different page, which looks like a broken selector.
- bws calls from Bot Screen-launched shells need `DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/$UID/bus`. Those shells inherit the screen's private bus, so `secret-tool` (the bws token bootstrap) returns nothing and bws fails with "Doesn't contain a decryption key". Keys are shown only once, so leave the key dialog open until `copy-to-bws` prints `verified True`. Then re-copy from the same dialog if the store failed.
- kchrome element tokens change on every `ls`, so click by label or `role:label` (e.g. `button:Create API Key`) and never by a token from an earlier call. Use `kchrome pclick LABEL` (real pointer click on the element frame) when a site ignores the accessibility click; Z.ai and Novita's Google buttons need it.
- On the Bot Screen, an Xfce "Failed to load the applications menu" popup can appear over the page and swallow clicks. If a click does nothing, screenshot :20 and close any desktop dialog with its own X before retrying.
- A Cloudflare "Verify you are human" checkbox (Turnstile) on a signup page is a CAPTCHA: tick the ToS box, record `needs-kevin` in the queue and batch it for Kevin's noVNC session. Never click the Turnstile box yourself.
- After a host reboot, `hermes computer-use screen start` brings back only the Xvnc desktop. CDP 127.0.0.1:9555 stays refused (`browser_exec` fails with "BU_CDP_URL unreachable") until you start `botscreen-chromium` yourself with the `systemd-run` line in `references/bot-screen.md`. Check readiness with `curl -s 127.0.0.1:9555/json/version`. The profile keeps its logins, so consoles open already signed in.
- If Kevin's Chrome, the Bot Screen Chromium or the `cua-botscreen` daemon is gone (screen idle-stop or host restart), relaunch each as a `systemd-run --user` unit before driving anything. Units: `kvn-chrome-botscreen` (`google-chrome-stable --ozone-platform=x11 --force-renderer-accessibility` with DISPLAY=:20 and the screen's XAUTHORITY), `botscreen-chromium`, `cua-botscreen` (`cua-driver serve --socket ~/.cache/cua-driver/cua-botscreen.sock`, without WAYLAND_DISPLAY). Delete a stale socket file first.
- Before redoing a site's signup under another identity, clear its site data with `bin/kchrome-forget <domain>...`; otherwise the old session cookie logs you back into the old account.
- `pkill -f <pattern>` from a shell whose own command line contains the pattern kills that shell; use `pgrep -x <name>` and kill pids.
