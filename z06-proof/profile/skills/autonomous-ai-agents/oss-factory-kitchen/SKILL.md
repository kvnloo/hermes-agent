# oss-factory-kitchen

Use when coordinating OSS factory repos, devices, phone waves, review loops, or cross-repo reporting.

## Rules

1. Keep one conversational coordinator and capability-based specialists. Reuse the canonical registry, repository roadmaps, routing/placement owners, measurement kernel, and existing queues rather than creating parallel authorities.
2. Keep personal history, inventory, informal preferences, credentials, and runtime state in a private overlay. Make public engine installs reproducible with fictional configuration; see references/factory-architecture.md.
3. Inventory canonical policy, deployed revision, native execution, and prior owner requests separately. Reconcile live sessions, claims, existing runs, and eligible tags before creating work.
4. Turn sufficient asks into bounded leaves with privacy, output mode, hardware, owner, destination, and verifier. Reuse proven dispatch paths; report planned, queued, app-sent, returned, and independently verified states separately.
   - A factory is "started" only when current tags have native send receipts or admitted host workers are executing. When every sender logs zero launches (hardware unavailable, foreground admission failing), lead the reply with that blocker, its exact reason and the unblock action; queue files, audits, reconciliation reports and unrelated side work are not a kickoff and must never be reported as one.
5. Use standing authorization for bounded downstream work and fork drafts. Gate promotion by repo policy and scoped owner approval; hold only the affected action.
6. Check burn-pace, exact entitlement, quota/reset state, and native harness before dispatch. Keep Claude workers in Hermes and GPT workers in fx/pi; keep Opus on core fixes/integration and Sol on bounded support, without paid fallback.
7. Keep code off generic free API scan lanes. Match app lanes to demonstrated capabilities: ChatGPT connector work versus DeepSeek source-packet text analysis without private connector access or execution.
8. Stage and review briefs before enqueueing. Verify branch/base, CG3 admission, non-overlap, and an actual canary send; deduplicate launched, claimed, unconfirmed, and parked tags during refill.
9. Use canonical phone launchers, shared UI locks, pacing, and foreground ownership gates. Reconcile ambiguous sends before retrying and requeue only proven unsent work under the launcher's valid tag procedure.
10. Gate Work/Codex Cloud separately from ordinary chats using the owner's authorization, mesh-idleness evidence, and measured weekly burn. Keep unrelated admitted phone and host lanes moving during a cloud hold.
11. Run heavy verification off groot through admitted fleet lanes and exact pushed SHAs. Re-run base/head tests, negative controls, combined gates, and parent review; use references/chat-pr-verification.md for returned PRs.
12. Use shared GitHub cache reads and preserve reserve holds. Verify result destination and exact-head approval before publication; report through Dash with stored-versus-delivered evidence and never expose notice tokens.
