# Hermes profile lifecycle (consolidate, back up, retire)

## When to Use
The owner wants a new role profile (chief of staff, a work lane, a specialist), to fold one profile into another, make a profile the main one, retire an old profile, or back up a profile without duplicating older backups.

## Creating a role profile
A profile is justified only when persona, skills or logins really differ. Never create one just to switch model or routing (that is a provider/model choice inside an existing profile; see token-thrifty-agent-routing). When the owner asks for several profiles, create only the one he named and have it (or you) propose the full profile map for his OK first, because each profile splits memory and history.
1. **Pin the model family end to end.** Set the default provider/model, then remove every path that could silently switch families: `fallback_providers []`, no model aliases pointing at other providers, `delegation.provider`/`delegation.model` on the same family, and every `auxiliary.*` helper (titles, compaction, review) on a small model of the same family. Read back with `hermes -p <p> config get model`, `... config get delegation`, `hermes -p <p> fallback list`. A model-only pin leaves children and helpers on the old route.
2. **Carry the owner's context engine and plugins.** Copy the profile-local plugins the main profile depends on (e.g. a handoff context engine) and set the matching config key (`context.engine`); a copied plugin dir without the config key is inert.
3. **Persona + standing context.** Write the role brief as a file under `data/operations/<topic>/` and point the persona at it. Seed USER and memory with the owner's standing rules (privacy, identity, model rules), consolidating to fit the cap.
4. **Small curated skill set.** Copy only the skills the role needs (a handful, never the whole library); skill load per session is the main context-rot cost, and a lean set keeps the profile usable by cheaper models later.
5. **Smoke test with a literal answer**, then confirm the session row in the new profile's `state.db` shows the intended provider and model. A reply alone does not prove the route.
6. **Hand it its first goal** on the surface the owner will use (e.g. the mobile app Bot Chat), as a short numbered brief whose first deliverable is a compact proposal for his OK, not unilateral changes to other profiles.
7. **Report** what is pinned and verified, the skills seeded, and what was deliberately not done (other profiles not created, the retiring profile's bot tokens and cron jobs not yet inventoried; use the retirement procedure below for those).

## Speed / free-provider profiles
- Probe live before picking a primary (receipt: `operations/speed-profiles-20261105/probe_all.py`). Free fast lanes die often (Cerebras 402, Groq TPD/8k TPM), so order `fallback_providers` by the target metric.
- Keys for a new profile: add a `hermes-<p>` scope to the deployed `bws-consumers.json` (back it up first), run `systemctl --user start bws-secrets-sync.service`, and set `secrets.command` to `~/.local/bin/hermes-scope-secrets hermes-<p>`. The `<p>` wrapper bypasses bws-env-exec, so without this the profile gets no keys.
- `hermes config set x none` writes YAML null, which means unset. Write the string with yaml directly.
- To keep `reasoning_effort` off the wire, set `model_overrides.<provider>.<model>.supports_reasoning: false` for both the named provider and `custom`, and leave the effort unset. Cohere compat rejects low/medium (422) and with `none` plus tools leaks its thinking into content. Hermes sends `default` to Groq, which gpt-oss rejects (400; recovery then costs one extra call).

- Secondary profiles run inside the default multiplexer gateway. Two things go stale there.
  - Its `secrets.command` snapshot is taken once per home, so a key added to the scope later stays empty. Point the profile's `.env` at the tmpfs scope file instead (`ln -s $XDG_RUNTIME_DIR/bws-secrets/hermes-<p>.env <profile>/.env`). Turns re-read `.env`, and this is a pointer, not a copy.
  - Plugins enabled after the gateway loaded the profile stay unloaded. Load them with the control verb `gateway.control_socket.reload_gateway_plugins(~/.hermes, profile_home=<profile>)`. Restarting the shared gateway is not needed.
- Tool Search defers plugin tools behind `tool_search`, and weaker models then report the tool as missing. Set `tools.tool_search.enabled: off` on lean profiles.
- Title generation is a second API call per session and halves the turns a 40-RPM free lane can serve. Turn it off with `auxiliary.title_generation.enabled: false` on rate-limited profiles.
- Speed evidence for the `ttft`/`tps` profiles and the `swarm` plugin is in `operations/speed-profiles-20261105/`. Cold `chat -q` costs about 1.9 s of Hermes CLI start before the request leaves. Warm turns (ACP/TUI) are the ones that beat pi and fx.

- Local models for a Hermes profile need at least 64K context; Hermes refuses smaller windows. The z0-farm router (8K) can't serve Hermes turns. Run a dedicated llama-server with `-c 65536*slots -ctk q8_0 -ctv q8_0 -fa on --cache-ram 512` and a MemoryMax (the default host prompt cache OOM-killed it at 6G). Qwen3.5-4B passed arithmetic and tool checks where Qwen3-4B-Instruct-2507 failed.

## Procedure
1. **Measure real use before calling a profile dead or alive.** Group its `state.db` sessions by month and `source`. Session counts lie: cron runs that wake on unchanged files, T3/ACP health-check pings (`source='acp'`, `message_count` 0, arriving in pairs per configured agent entry) and scripts calling `hermes` without `-p` all create sessions in a profile nobody uses. Count sessions with `source in ('local','tui','cli','telegram') and message_count>2` as owner use. Report per month: total and owner-started.
2. **Find every caller (read-only inventory).** Delegate one read-only worker to write `INVENTORY.md` + `MIGRATION-PLAN.md` under `data/operations/kitchen/<run>/`. It covers config and `.env` key diffs (names only), cron jobs, skills diffs by name+hash, memories, MCP servers, bot-token ownership (compare hashes, never print tokens), systemd units, scripts and T3 agent entries that reference the profile (`rg -l`, skip node_modules), and disk size.
3. **Check what pins the profile.** `hermes profile use <p>` only rewrites `~/.hermes/active_profile`. `HERMES_HOME` wins over it and is exported from `.files` (`environment.d/hermes-home.conf`, `.zshenv`), so bare `hermes` keeps hitting the old profile until those change. Other shared tooling can live inside a profile dir (e.g. `bws-env-exec` using `<profile>/bin/bws` for every profile's secrets). Repoint those before any deletion, or secret refresh breaks everywhere: make the tool resolve its binary from an env override, then PATH, then a shared install outside any profile (`~/.hermes/tools/...`), and export the override (`BWS_BIN`) in environment.d so copies already deployed from an older branch stop using the profile path too. Test the deployed copy (`readlink -f ~/.local/bin/<tool>`), not only the repo copy; they can come from different branches. Change both the live user session (`systemctl --user set-environment` / `environment.d`) and the shell rc (`~/.zshenv`, backup next to it), then make it permanent as a `.files` draft PR; a live-only edit reverts at next login. Verify by running the secret refresh for every scope (count them; all must succeed) and a bare `hermes` resolving to the target profile.
4. **Back up only the delta against existing backups** (owner rule: there are already backups; don't repeat them). List `/mnt/zer0models/hermes-backups/` (full-zip receipts, the verified CAS archive `compact-*`, `profile-keep-*`) and `/mnt/zer0models/backups/` first, and say what each covers and the newest full copy's date. Then run the delta tool against the CAS base; see `references/delta-backup.md`. Run it as a transient unit (`systemd-run --user --collect -p Nice=10 -p MemoryMax=6G ...`), not in the terminal, where long compression jobs get killed.
5. **Migrate in reversible order:** delta backup → repoint shared tooling → repoint units/scripts/T3 entries → copy skills (the union of recently used and historically most-used, ranked from the source's `state.db` skill_view calls; never overwrite a copy the target already has; watch for same-path name collisions) → pause (don't delete) the source's still-active cron jobs → promote only memory entries the target lacks, putting standing owner rules (privacy, identity) in the target's USER memory, consolidating if it is at the cap → switch `HERMES_HOME`/active profile → re-authorize integrations the target lacks (OAuth such as Linear for kanban sync is an owner action) → remove the source's T3 provider/agent entries → 7-day observation → archive or `hermes profile delete`. Never merge one profile's `state.db` into another's; history stays searchable via ctx and the backup.
   - Report retirement as a checklist of steps done vs left (with evidence per step); "moved to clean" is not done while the T3 entry, OAuth or observation window remain.
6. **Owner decisions to batch, not assume:** which profile owns each bot token, which MCP/integrations to carry over, whether stale cron jobs move, and archive versus delete at the end.

## Pitfalls
- When `hermes update` or `hermes doctor` warns that gateways still run pre-update code after a restart, check `hermes update --plan` per process. A service that can't publish its code identity (e.g. a separate API-only host) keeps the warning alive even though the main gateway is current.
- A new profile already ships bundled skills (e.g. `hermes-agent`). `cp -r <src>/hermes-agent <new>/skills/.../hermes-agent` then nests a second copy inside the bundled one (two skills, one name). Remove or move the bundled dir first, and check with `fd SKILL.md` that no dir sits inside a same-named dir.
- Kick off a bot's chat with a short `hermes -p <bot> chat -c "Bot Chat" -q ...` only for quick turns. A long `-q` run holds the chat's session lease, so messages the owner sends from the app or dashboard sit queued (shown as sent) until it exits. For long work, send the kickoff and arm `/goal` through the same route (`-q "/goal <text>\nverify: ...\nstop when: ..."` is processed by the gateway's shared goal handler); the gateway then continues the work and app messages preempt it.
  - With a standing `/goal` active, a `-q` from the CLI can wait indefinitely behind back-to-back continuation turns. To message a busy bot, queue a bot DM instead (no lease, delivered at the next turn boundary): `HERMES_HOME=<sender profile> venv/bin/python -c "import tools.bot_mode_dm as m; from tools.bot_relay import _hermes_cli; m._start_delivery([_hermes_cli(),'-p','<bot>'], 'Message from 🤖 <sender> (@<sender>): <text>', '@<bot>', stdin_file=False, profile_home=Path.home()/'.hermes/profiles/<bot>', author={'id':'bot:<sender>','name':'<sender>','is_bot':True}, task_id=None, agent=None)"` (the public `message_agent_tool` refuses outside a Bot Chat session).
  - A `-q` sent while the bot is mid-turn takes the chat's `cli` lease and waits for its turn; until it returns, every other `-q` fails with "This chat is open in another Hermes window" and app messages queue. Send one combined message per turn, and kill stale waiters (`ps -eo pid,args | rg 'hermes -p <bot> chat'`) before the next send. Raise `goals.max_turns` (default 20) for a multi-lane mandate, and confirm the goal by reading `state_meta` key `goal:<session>` in the bot's `state.db` (`status: active`, contract fields filled).
- Make the goal headline point at a brief file ("read AYO-BRIEF.md first") and add later asks to that file as numbered items. A `-q "/subgoal ..."` sent while the bot is mid-turn waits behind that turn, so a short `timeout` kills it undelivered; send it as a background run with a long timeout and `notify`, then check `subgoals` in `state_meta`.
- When the owner says a bot "isn't replying", read the bot's `state.db` first (`messages` for its Bot Chat session, `role='assistant'`, newest first) before touching the app. Replies present there mean a client render problem, not a silent bot: forward the pending reply with `hermes -p <sender> send --to telegram --subject ... --file <txt> --json`, and if it persists add a small relay timer (assistant rows with `finish_reason='stop'`, `id > last_id`, state file for `last_id`) until the client is fixed. Don't open the app to debug while the owner is using that phone.
- When a lane bot reports back, its message lands in the chief's chat as `Message from 🤖 <lane>` and wakes it; check those in the chief's `gateway.log` (`inbound message`) rather than polling each lane.
- New profiles default to `approvals.mode: smart`, which blocks script execution in unattended turns ("BLOCKED: Command flagged as dangerous"). Match the parent profile (`off` in clean) for bots that must run on their own.
- `hermes backup` only writes whole zips and `--keep` prunes old ones; it can't extend an earlier archive. Use the delta tool until upstream gains an incremental mode.
