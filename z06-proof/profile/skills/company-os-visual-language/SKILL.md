# CompanyOS visual language

Recover the approved visual implementation before inventing a replacement. Run `git log --all -- web/index.html plugin/plugin.js`, inspect candidate revisions with `git show <ref>:web/index.html`, and compare their committed screenshots to current rendering. Trace static HTML and the functional plugin separately: an approved style can exist only in the prototype while later runtime work retains a different renderer. Recover visual primitives in an isolated candidate, prove the style in a browser, then integrate the existing dynamic adapter without discarding its behavioral fixes.

Use docs/inspo/hud-light.jpg and hud-dark-cockpit.jpg as visual references. Ignore compression artifacting: build crisp SVG/CSS geometry, not grain or distressed screenshot textures. Style consists of thin corner brackets, dotted rings/connectors, small circular/diamond nodes, instrument typography, restrained accents, near-black dark and warm-white light surfaces. Recovered v3 uses local IBM Plex fonts.

This HUD language is Kevin's default taste for dashboards, briefs and explainers: when he asks for an artifact "in design I like" or to explain a project visually, use it rather than inventing a palette. It is NOT the whole look for creative tools (film/video studios, editors, direction labs): there he wants colourful and fun, and a grey-panels-plus-one-green-accent HUD reads as lacking even when the UX is excellent. For those, let the content be the hero (large poster-like canvas, display + serif type, warm paper vs near-black contrast), colour-code meaning (shot types, beats, chapters), use visual preview cards for choices instead of forms, use the craft's vocabulary (Cut, Takes, Screening room, Loop shot), and keep HUD only as accents (corner brackets, mono micro-labels). Compare against the approved earlier version side by side before claiming a redesign is done. For explainer/briefing artifacts (multi-repo overviews, strategy briefs), follow `references/hud-explainer-artifacts.md`.

For consumer/mobile product apps (room planners, phone tools), Kevin wants the zerOS look: Living Night tokens with liquid-glass surfaces and a premium gold accent, not a generic dark panel UI with emoji. Reuse zerOS's own files: copy `packages/ui-foundation/{tokens,product-bridge,primitives}.css` into the app (note the source commit), vendor Hanken Grotesk / Cormorant Garamond / IBM Plex Mono via `@fontsource/*`, build on `.z-seg`, `.z-icon-btn`, `.z-btn`. Verify with phone-viewport screenshots before claiming a redesign is done. For React Native/Expo apps like Dash, CSS can't be copied. Port `tokens.json` (the authority) into the app's typed theme, converting oklch to hex once with a comment. Load the three families via `@expo-google-fonts/*` and `expo-font`. Build glass with `expo-blur`, using a tint layer, a rim top border and a hairline, and cap concurrent BlurViews on Android. Keep the app's own information architecture: restyle only palette, type and surfaces. The approved phone-grammar reference is the garden-room capture set under `project-artifacts/garden-room/`. A repo design doc that bans a "zerOS palette" means an invented cyan/violet one; the real tokens are warm night plus gold. For any web artifact "in Dash's design language", work from the build the owner's phone actually runs, not the newest worktree by commit date. Several worktrees share the same palette but differ in component treatment. Don't work from Dash's `DESIGN.md`/`docs/design/language.md` either: those still describe pure black and system UI. Matching tokens alone still looks "slightly wrong" to the owner, because the liquid-glass and gold-pill effects live in the components. Follow `references/dash-web-port.md`: find the phone tree, sample its real screenshots, then copy the component recipes. The shipped app uses:
- flat warm night `#0c0c0a` (no ambient vignettes) with cream ink `#ECE8DF`;
- Cormorant Garamond for titles and numbers, Hanken Grotesk for body, IBM Plex Mono only for paths and tokens;
- gold `#d7b986` rendered at 68% with a light rim, used only for the nav pill, count badges and the primary action. Selected segments and chips are neutral glass, not gold;
- glass surfaces (fill plus top sheen gradient, a hairline with a brighter top edge, and a drop shadow), silver orb avatars and status dots.

An all-monospace terminal page is not Dash's style. Write the analysis as a design contract in the repo (`docs/design/<name>.md`) before dispatching implementation, so workers follow one spec.

Treat style independently from content/layout density. Kevin prioritizes the design language; let panes and density adapt to actual dashboard content rather than forcing the reference's sparse composition. Keep dynamic truth/privacy/freshness semantics intact while restyling. Do not copy fake telemetry, progress, voice activity, or authority indicators from inspiration images.

For layout selection, build an interactive artifact with multiple functional arrangements, light/dark themes, browser-rendered comparison images, clickable inspection and locally persisted selection. Use real existing read-only sources; label static previews explicitly. Open the verified artifact in the user's existing Zen browser when requested, rather than only giving paths.

Refresh the user-designated reference issue and all comments before implementing or declaring media unavailable. Retrieve the actual attachment and inspect labeled early/middle/late frames; never infer visuals from prose or reuse a stale missing-attachment conclusion. Preserve the source hash and frame timestamps, and report which observed visual patterns were implemented separately from unimplemented or unseen interactions.

Keep the backend as the sole data authority in a design chooser. A fixed same-origin loopback GET proxy may expose only snapshot/health, preserving bytes and rejecting client credentials, redirects, mutations and arbitrary paths. Capture real browser images in both themes; label the gallery as captured views, not current telemetry. Local choice must explicitly leave production unchanged.

Define an operator-purpose matrix before wiring or drawing a pane: operator question, existing source/read contract, representative group, drilldown, evidence boundary and missing-source behavior. Inspect the configured system APIs and source-owned projections before declaring a contract absent; distinguish available on a branch from loaded live. Do not create replacement producers merely to fill a panel.

Use compressed source groups and progressive child inspection instead of making a dense dashboard a wall of labels. Make every drawn node or arrow a working control, with breadcrumbs/back, actual child rows and provenance/freshness/coverage. Test selected identity, disclosure state and keyboard focus across polling; replacing a DOM subtree can preserve selection while silently discarding focus. Keep control nodes mounted or restore focus via stable identifiers.

When integrating a verified backend and standalone inspection adapter into a styled view host, import those exact artifacts instead of cherry-picking a conflicting renderer. Preserve existing preference keys and schemas; when all layouts are retained, present selection as switching views and saving a default, not eliminating finalists. Keep generated-model provenance explicit when its generator belongs to another source lane. Bind pod inspection to namespace plus name, not display name alone. Re-run the narrowest responsive viewport after changing button copy: longer default-view labels can overflow even when all operational panes fit.

Read `capacity_plane` for host/session/offer/lease records; the existing backend's legacy `capacity` array aliases providers and must not be presented as host capacity. Preserve null/false/zero and empty-state distinctions. Do not infer tasks, authority, model qualification or idle capacity from process/service presence.

Scope boundary (owner rule): Company OS visualizes and controls INFRASTRUCTURE (hosts, k3s nodes/pods, services, tailnet, repos/branches/deploys, queues/quotas/capacity, model/SLM serving and routing, and the evals that justify that wiring). Dash is the agent control plane (chats, sessions, approvals, bots, voice, steering). Never put chat, agent approvals or session steering in Company OS; link out to Dash. Infra controls (cordon a node, restart a service, re-run a job, promote an SLM lane) must be explicit, confirmed and logged; ship read-only first and list proposed controls.

North star: a living map whose structure comes from z0archy's compiled world model, animated by the live backend (activity, health, traffic), with a bottleneck/critical-path view, a WHY link from every routing node to its z0evals study, SLM capability ladders as achievements, and one batched 'needs Kevin' lane. Owner's xyflow reference: /mnt/zer0models/zer0-projects/clients/autopilot/archy-flow (per-node score + research state, simplify/reuse/risk lenses) — borrow ideas, drive scores from evidence not LLM opinion.

Showing it live:
1. Find the newest branch with live data, as described above.
2. Run it as a user unit, so it survives the chat: `systemd-run --user --unit=company-os-live --slice=agent.slice -p MemoryMax=1G --setenv=KUBECONFIG=/home/kvn/.kube/k3s.yaml --working-directory=<worktree> <hermes venv python> scripts/integrated_chooser.py --port <free port>`.
