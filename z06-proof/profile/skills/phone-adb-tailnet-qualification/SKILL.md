# Real Android ADB over Tailscale

## When to Use

Use for real-phone wireless debugging, Phone Harness plugin qualification, or safe shared-checkout phone test helpers.

## Phone app setup sequence

1. Resolve the official product/distribution source before selecting an APK; similarly named community clients and catalog adapters are not proof of the official app's source. For Hermes mobile, start with the official site's `/mobile` page and follow its platform link. Report an unlocated public repo as unlocated, not proven private or closed-source.
2. Verify the exact phone's ADB state and hardware identity; apply the pairing and bounded reconnect rules below. Do not make the owner repeat supplied setup inputs before trying them.
3. Check whether the app is already installed before downloading or enrolling in a distribution service: `adb -s ENDPOINT shell pm list packages --user 0 FILTER`, then package-scoped `dumpsys package` for version and `cmd package resolve-activity --brief --user 0 PACKAGE` for its launcher. Explicit `--user 0` avoids unrelated work/private-profile permission errors. Never replace or uninstall an existing installation merely to get through setup.
4. Check keyguard state, launch the resolved component, and inspect only the authorized app's hierarchy. After each action, discover the foreground activity again: an empty app-filtered hierarchy can mean a browser custom tab or system permission prompt, not a failed click. Inspect that specific surface before retrying, and avoid unrelated browser text.
5. For self-hosted clients, discover the existing listener and reverse-proxy/Tailscale Serve route rather than starting or exposing another server. Verify health and public auth discovery separately. In Hermes, `/api/health` and `/api/auth/providers` identify reachability and offered login methods; a 401 from a guessed auth-status URL does not establish a broken login flow.
6. Select a login method the server actually advertises. Browser login may open a provider-choice page followed by a credential form; verify each transition before calling it stuck. Leave password entry to the owner or the supported private credential mechanism—never extract credentials or reset authentication to skip onboarding.
7. Continue through the actual authenticated workflow rather than stopping at the next owner-facing screen. Report pairing, app presence/version, server reachability, sign-in-page arrival, authenticated connection and a real chat turn as separate milestones. A login page is not a working app connection, and a retry reaching it does not establish the cause of an earlier failure. When the owner reports failed sign-in, trace the exact attempt through provider login, native code redemption, WebSocket negotiation and application traffic before asking him to repeat setup; ask only for a genuinely required private interaction or missing decision.
8. After an OAuth callback, wait for a bounded success/error condition before pressing Connect again or restarting the app, because repeated submissions can invalidate pending native-login state. Correlate each attempt with the selected profile's auth events; login success without token redemption and token redemption without a usable chat socket are different failure boundaries. If the owner confirms recovery, stop driving the phone and verify with read-only evidence rather than disrupting the working session.

## Qualification rules

- Load `hermes-agent` and `maestro-local-android` before plugin/setup work. Read official Hermes plugin docs; use the supported plugin CLI scoped to the active profile, not hand-edited config or another profile. Never restart the owner's running CLI.
- Disambiguate automation plugins from similarly named APK workflows and Tern UI plugins. A catalog `phone-harness` entry can be the actual Hermes plugin even when older history points at a `phone-controls` guest. Verify its manifest, catalog SHA, package version, enabled status and doctor output separately.
- Exercise the actual `phone_exec` child once with a pinned metadata-only readiness call: plugin doctor can pass import/registration while its raw `[sys.executable, '-m', 'phone_harness.run']` child fails `ModuleNotFoundError` under a bootstrapped Hermes installation. Compare `hermes --run-module phone_harness.run` with the same explicit Android environment to isolate bootstrap/dependency resolution from ADB. Report tool failure separately from successful CLI readiness; do not claim a restart will fix it or silently patch a pinned vendor plugin.
- Inspect current Tailscale peer state by IP rather than exact HostName: friendly names can differ from DNS names. Recheck `adb devices -l`; an earlier connected transcript does not establish current connectivity.
- Android wireless pairing and connection ports differ. When the owner explicitly supplies an ADB pairing code and endpoint for setup, use that authorization rather than asking him to repeat the same information or perform the pairing himself. If the active tool permits ADB pairing, submit the code to `adb pair HOST:PAIR_PORT` through stdin, not as an argv argument; suppress code echoes and never save it in scripts, receipts or skills. Do not solicit codes in chat or generalize ADB pairing authorization to screen-lock PINs, passwords or account 2FA. Honor stricter active-tool restrictions and explain the exact restriction when one blocks execution. Try the supplied tailnet endpoint before requiring same-Wi-Fi pairing; use a LAN pairing endpoint only when the observed failure calls for it.
- Keep shared ADB servers intact during connectivity diagnosis. If testing a different installed SDK client, isolate its server on a confirmed free owned port and clean up only that owned process. Some adb versions reject `-L tcp:127.0.0.1:PORT`; `-L tcp:PORT` is the supported loopback-listener form. Verify the server actually listens before treating failed client requests as phone authorization evidence. Do not keep scanning after bounded reconnect attempts fail.
- mDNS is same-LAN discovery, not tailnet discovery. Restrict discovered service names to the known hardware serial and `_adb-tls-connect._tcp`, connect through the known tailnet IP, then verify get-state and hardware serial. Never scan other hosts or silently select another phone. Wireless-debugging connect ports change when the phone toggles debugging or reboots, and over the tailnet mDNS can't see the new port. In that case, scan only the known phone's tailnet IP (`nmap -Pn -p 30000-49999 --min-rate 3000 <ip>`), `adb connect` each open port, keep the one that reports `device` with the expected `ro.serialno`, disconnect the stale `offline` entries, and update the persisted endpoint state (e.g. `~/.local/state/z0live/phone-adb.json`). Brief workers to read the endpoint from that state rather than a hardcoded port. If candidates remain `offline`, do not infer that the owner must re-authorize solely from that state. Complete an already-authorized pairing attempt first, then retry the bounded connection-port candidates: pairing can authorize a port that failed before it. Disconnect/reconnect only the stale target endpoint if needed, never the shared ADB server. If no candidate becomes authorized after that pass, stop scanning and ask for the current connection IP:port or acceptance of a visible authorization prompt.
- Wireless debugging turns itself off when the phone drops Wi-Fi, and its port changes on every re-enable. For a phone that must stay reachable unattended (factory sender, test rig): rediscover it on the LAN (`avahi-browse -rpt _adb-tls-connect._tcp`, keep only the known serial), `adb connect` that port, then `adb -s <ep> tcpip 5555`. Legacy TCP adb on 5555 then answers on both the LAN and tailnet IP and survives Wi-Fi drops until the next reboot. Point workers at `<tailnet-ip>:5555`, verify `ro.serialno`, and give the owning lane a watchdog that reconnects and re-runs `tcpip 5555` after a reboot.
- To hand the owner a link or list on the phone: put it at a URL the phone can reach (for a list, a secret `gh gist create` markdown file renders tappable links that open in the native app), then run `adb -s ENDPOINT shell am start -a android.intent.action.VIEW -d URL com.android.chrome`. Re-check `dumpsys activity activities | grep topResumedActivity`: if the owner is busy in another app, the intent can land behind it. Don't fight the foreground; tell him the link instead.
- Stop reconnect fallback on a hardware mismatch. ADB connect exit zero/message is insufficient; verify authorized state and exact hardware. Persist only validated endpoint/identity in private atomic state.
- Export the exact ANDROID_SERIAL and Android platform for the new agent, with telemetry and classifier auto-run disabled. Use `reconnect && env_text="$(phone-adb env)" && eval "$env_text" && hermes --profile clean`, not unguarded `eval "$(...)"`, which can succeed after an empty failed substitution.
- A pinned wrapper must refuse server-global ADB commands and target overrides; `-s` alone does not make `kill-server` device-scoped. Shell/install/capture capabilities still require owner approval; the wrapper and Python plugin are not sandboxes.
- Qualify CLI behavior with deterministic tests for identity/port validation, offline fail-closed dispatch, interactive pairing without saved codes, safe exports, and hardware-mismatch fallback. Label mocks as deterministic tests, not live-device proof.
- Ask before installs, role/HOME changes, microphone and screenshots. Owner unlocks manually; never bypass lock/security prompts. Use approved test screens, filtered hierarchies and tag-scoped logs only. No personal data or cloud fallback; serialize ownership across processes.
- For the official Hermes mobile beta, distinguish Nous Cloud enrollment from self-hosted dashboard login. A cloud account showing no agents is not a Google authentication failure. After self-hosted OAuth succeeds, require native token redemption and a working chat WebSocket; an open login page or minted ticket is insufficient. Resolve the dashboard's selected profile from its process/open log files, since `--open-profile` can put auth evidence outside the launch profile.
- Preserve WebSocket subprotocol negotiation in a dashboard proxy. The mobile client requires `hermes-gateway-v1`; a proxy that upgrades downstream without a selected protocol can make the app close with 1002 after successful Google login. Negotiate upstream first, pass offered protocols through the WebSocket client's protocol API rather than raw handshake headers, return only the upstream-selected protocol downstream, and propagate rejected upstream handshakes before sending 101. Test mobile negotiation/echo, ordinary browser sockets, and rejected authorization before activating only the proxy service. Compare the upstream and downstream selected protocol rather than treating an HTTP 101 as success. Do not restart the shared Hermes owner for a proxy-only repair or log credential-bearing ticket subprotocols. For temporary diagnostics, log only method, route without query, status and redirect host/port; redact ticket subprotocol values before printing existing logs. Remove temporary instrumentation and state whether removal is active or only saved for the next process start—an on-disk cleanup does not change a running process.
- Verify the APK workflow's exact source SHA and signer/package. A successful old experiment artifact is not proof of a new adapter; branch filters can exclude the feature branch. Never uninstall on signing conflicts.
- In shared checkouts, stage exact owned paths and commit with `git commit --only -- <paths>` so a peer's staged backend files are excluded. Verify commit paths and preserve peer state. Record current blockers separately from historical successes.
